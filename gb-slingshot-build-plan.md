# Game Boy Slingshot Game: Build Plan (GBDK-2020, C)

Working title: **GB-Slingshot** (see "Theme and IP" below before settling on art and names).

## Goals and scope

A single-screen-per-level slingshot/destruction game for the original DMG Game Boy. Fling a limited number of projectiles at structures built from wood, stone and ice, and knock out every target. No game engine, same approach as GB-Protector and GB-Draughts.

**v1 scope:** 3 projectile types, 3 materials plus targets, 30 levels, title screen, level select, battery save for stars, SFX.
**Stretch:** music, SGB border, 100+ levels, GBC colour palette.

## Theme and IP

Angry Birds characters and name are trademarked, so build with original characters (for example, a different animal launched at a different kind of target). The mechanics are not protected, the look and names are. Settle this before drawing any art.

## Architecture overview

| Layer | Approach |
|---|---|
| Structures | 8x8 cell grid on the background layer; each cell has a material and an HP |
| Projectile | Sprite with 8.8 fixed-point position and velocity (int16) |
| Flight arc | Pre-computed lookup tables generated by a Python script at build time |
| Collision | Projectile position maps to a cell index, so it is a single array lookup |
| Collapse | Stepped gravity on cells, a few cells per frame, not a physics engine |
| Levels | RLE-compressed cell data in banked ROM (MBC1) |
| HUD | Window layer (shots left, score, target count) |
| Save | MBC1 + RAM + battery, one byte of stars per level |

The world is one screen wide in v1 (20x18 tiles). Keep a 32-wide BG map in mind so a short horizontal pan to the target is possible later.

## Key technical decisions

**Fixed-point maths.** Use 8.8 (int16_t) for position and velocity. Gravity is a constant added to vy each frame. No floating point anywhere.

**Aiming.** The player adjusts angle (d-pad up/down) and power (d-pad left/right, or hold A and release). Angle and power index a table of launch velocity pairs (vx0, vy0). A 16-step angle by 8-step power table is 128 entries of 4 bytes, tiny. The same table drives the dotted preview arc, drawn as 3 to 5 sprites sampled every N frames of simulated flight.

**Cell grid.** Each cell is one byte of material plus one byte of HP, held in a RAM array (about 20x18 = 360 cells, 720 bytes). Materials: empty, wood, stone, ice, target. Each has a base HP and a damage multiplier.

**Damage model.** On impact: `damage = speed_squared_bucket * material_factor`. When HP reaches 0 the cell is removed, and the projectile loses some velocity or stops, depending on type and what it broke. Compute speed buckets with a lookup, not a square root.

**Collapse rule (staged).**
1. *Column gravity:* any cell with an empty cell below drops one cell every few frames. Simple, deterministic, enough for a playable game.
2. *Support rule:* a cell with nothing below stays put only if both horizontal neighbours are solid. This gives bridges and overhangs a believable feel.
3. *Impact damage:* a cell that falls more than 2 cells damages whatever it lands on.
Cap the number of simultaneously moving cells (about 8). If more would move, snap the extras instead of animating them, so you never exceed the sprite budget.

**Sprites and OAM.** 40 sprites total, 10 per scanline. Budget: projectile 1 to 2, preview arc 5, falling cells up to 8, particles up to 10, slingshot and UI few. Static structure cells live on the background layer and are redrawn with `set_bkg_tile_xy` when destroyed.

**Frame budget.** About 70,000 CPU cycles per frame at 59.7 Hz. Run the collapse step on a fixed interval (every 4th frame, for example), not every frame, and process a limited number of cells per step.

**Banking.** Start unbanked. Move level data to MBC1 banks once it exceeds about 16 KB. Use `#pragma bank` and `SET_BANK`/`SWITCH_ROM`, with a single level-loading function in bank 0 that copies the level into the RAM grid.

**Audio.** SFX by writing directly to the APU registers via small helper functions (launch, hit wood, hit stone, hit ice, target pop, win, lose). Music via hUGEDriver as a stretch goal.

## Build phases

Each phase ends with something you can run in mgba.

### Phase 0: Skeleton (about 1 session)
- Copy the Dockerfile, Makefile and folder structure from GB-Protector.
- `main.c` shows a background and a bouncing sprite; `make` and `make run` work.
- **Done when:** ROM boots in mgba from a clean checkout.

### Phase 1: Simulation core, host-tested (1 to 2 sessions)
- `sim.h`: grid, materials, HP, projectile state, fixed-point flight, cell collision, damage.
- `tools/mktables.py` generates the launch table.
- `tests/test_sim.c`: flight reaches expected landing points for known angle and power, a stone cell takes more hits than wood, ice shatters from one fast hit, win condition triggers when all targets are gone.
- **Done when:** `make test` is green with no hardware code involved.

### Phase 2: Rendering and aiming (1 to 2 sessions)
- `mkgfx.py` produces tiles for ground, wood, stone, ice, target, projectile, slingshot, aim arc dot.
- Draw one hard-coded level from the grid.
- Aim with the d-pad, fire with A, projectile flies and collides, cells break and disappear.
- **Done when:** you can fling at a hard-coded tower and knock it down.

### Phase 3: Collapse and game loop (2 sessions)
- Column gravity, then the support rule, then fall damage.
- Win and lose states, shots remaining, splash screens (same pattern as the Battleship end-of-round splashes).
- Window HUD.
- **Done when:** one level is fully playable from first shot to win or lose.

### Phase 4: Levels and progression (2 sessions)
- `mklevels.py` reads ASCII files such as `W` wood, `S` stone, `I` ice, `T` target, `.` empty, and packs them with RLE.
- Level select screen, star rating (based on shots left), 10 levels first.
- Battery save of stars.
- **Done when:** you can play levels 1 to 10 in order and the stars persist after a reset.

### Phase 5: Projectile variety (1 to 2 sessions)
- Type A: standard.
- Type B: speed boost on a second A press (more damage to stone).
- Type C: splits into three on a second A press.
- Optional type D: explosive, damages a radius of cells.
- Each ability is a few lines in `sim.h` plus tests.
- **Done when:** levels 11 to 20 each need a particular projectile type.

### Phase 6: Polish (open-ended)
- Title screen, particle puffs, screen shake on big collapses, sound effects.
- Super Game Boy border (reuse `sgb_border.c/h`).
- Levels 21 to 30 and a difficulty pass.
- Optional: hUGEDriver music, GBC palette.

## Testing strategy

- **Host tests** for everything in `sim.h` (flight, collisions, damage, collapse, win/lose).
- **Golden-replay tests:** record a sequence of (angle, power) shots per level and assert the final cell grid hash. This catches regressions when you tweak collapse rules.
- The replay only covers what it asserts — and a miscompiled front end can corrupt what it reads back: with the SDCC cached-accumulator bug, the state-change block wrote the comparison difference into `last_state` every other settle frame, so a splash drew or not depending on where a shot's settle frames happened to stop. The golden replay's recorded game and its lose replay happened to land on the draws; the early-win session in `tests/emu_replay.py` (level 1, one shot, 3 stars) covers the other branch — the multi-star splash rows and star banking the golden game never shows. `make check-asm` guards the miscompile itself on whichever toolchain builds the ROM (see the compiler note in the README).
- **Level solvability check:** a script that brute-forces the angle/power table per level and reports whether any shot sequence can win, so you do not ship unwinnable levels.
- **Manual play** in mgba each phase, plus a check on real hardware or a flash cart before release.

## Risks and how to handle them

| Risk | Mitigation |
|---|---|
| Collapse feels wrong or floaty | Keep it deterministic and tunable via constants; golden-replay tests make tuning safe |
| Too many moving sprites | Hard cap on moving cells; snap the rest |
| Slowdown on big collapses | Interval-based collapse stepping, per-step cell limit |
| Levels too easy or impossible | Solvability script, then playtest |
| Scope creep | Ship Phases 0 to 4 as a complete game before adding projectile types |
| IP trouble | Original characters and name from the start |

## Suggested first step

Phase 0 and Phase 1 together: get the skeleton building, then write `sim.h` and the launch table generator with tests, before touching any graphics. A correct, tested core makes everything after it faster.
